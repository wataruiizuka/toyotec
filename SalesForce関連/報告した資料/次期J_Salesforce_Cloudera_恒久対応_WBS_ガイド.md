# 次期J Salesforce→Cloudera 恒久対応 WBS ガイド

## 1. このガイドの目的

本ガイドは、提出資料 **「次期J_Salesforce_Cloudera_恒久対応_WBS.xlsx」** を初めて見る方でも、

- このWBSが何を目的としているのか
- どのシートを見れば何が分かるのか
- どこが確定事項で、どこが未確定事項なのか
- WBSをどのように更新・管理すればよいのか
- STEP1のPoCとSTEP2の230組織展開をどのように分けて考えるのか

を理解できるように整理した説明資料です。

本WBSは、**TMTを先行対象として、Salesforce（LPP）のデータ変更をイベントベースでAzure側に受信し、Cloudera DWHまでニアリアルタイムに連携できるかを検証する恒久対応PoC**を管理するためのものです。

> **重要**：本WBSは「最終アーキテクチャ・正式納期・正式工数がすべて確定した実行計画」ではありません。  
> 現時点で未確定の要件・方式・担当・工数を明示したうえで、PoCを前に進めるための管理資料です。

---

## 2. このWBSで実現したいこと

### 2.1 背景

次期Jでは、販売店の活動計画・活動実績等のSalesforceデータを、ポイント施策等で利用できるようデータ基盤側へ連携することが検討されています。

現状の課題を踏まえ、恒久対応では次のようなイベント駆動型の連携をPoCで検証します。

```text
TMT Salesforce（LPP）
        ↓
対象データの作成・更新等
        ↓
Salesforce CDC / Event Bus 等
        ↓
イベント配信
        ↓
Azure Event Consumer
        ↓
Azure → Cloudera連携
        ↓
Cloudera DWH
```

ただし、上記は**現時点の基本構想**です。CDCとPlatform Eventの具体的な使い分け、Subscribe方式、Azureサービス、Clouderaへの投入方式などは、WBS内で確認・決定する対象として管理しています。

### 2.2 STEP1とSTEP2

本WBSでは、検証を次の2段階に分けています。

| 区分 | 内容 | 本WBSでの扱い |
|---|---|---|
| STEP1 | TMTを先行対象としたSalesforce→Cloudera PoC | 今回の主対象 |
| STEP2 | 230組織への本格展開 | 後続・スコープ外 |

STEP1では230組織すべてを実装するのではなく、**TMTで実現性・性能・障害時挙動・Salesforce制約・コスト条件等を確認し、230組織へ展開できるか判断するための材料を取得する**ところまでを対象としています。

## 3. 最初に確認してほしい重要事項

本WBSを読む際は、次の点を確定事項として誤解しないようにしてください。

### 3.1 2026年9月30日は正式納期ではない

WBS上では **2026/09/30** を仮完了日として配置していますが、これは「9月中の上位報告」を基準に逆算するための**計画上の仮アンカー**です。

正式な納期・報告日は関係者確認後に更新します。

### 3.2 工数は未算定

今回のWBSでは正式工数を確定していません。

旧Salesforce→NiFi→Kudu先行検証で使用していた **53.5人日** は、今回のSalesforce→Azure→Cloudera PoCとは方式・対象・成果物が異なるため、そのまま流用していません。

正式工数は、少なくとも以下が確定してから再見積します。

- PoC対象Object数
- PoC対象Field数
- Salesforceイベント連携方式
- Subscribe方式
- Azure Event Consumerの実装方式
- Azure→Cloudera連携方式
- 性能・障害試験の範囲
- 担当体制

### 3.3 技術方式は一部未確定

現段階で「必ずこの方式を採用する」と確定していないものがあります。

- CDC Change Eventを直接Subscribeするか
- 別途Platform Eventを利用するか
- Pub/Sub API / CometD / MuleSoft等のどれを採用するか
- Azure側の具体的サービス
- Azure→Clouderaの具体的な連携方式
- Cloudera側の受入インターフェース・保存形式

そのため、WBSではこれらを**「実装タスク」だけでなく「方式確認・方式決定タスク」から管理**しています。

- PT-06：Replayによるイベント再取得確認
- PT-07：重複受信・二重処理挙動確認

「不要」という意味ではなく、**9月中報告から逆算した際に優先順位を調整できる項目**です。

#### スコープ外・後続

STEP1では実装対象にせず、TMT PoC完了後のSTEP2で別途計画するタスクです。

- FUT-01：230組織向け詳細アーキテクチャ設計

## 7. WBSの10領域を理解する

### 7.1 プロジェクト管理（PM）

**目的：PoC全体を止めずに管理する。**

主な内容：

- WBS・大日程の更新
- 進捗・課題・リスク管理
- Salesforce / Azure / Cloudera関係者との調整
- 成果物・設計レビュー
- 最終的なGo／No-Go管理

この領域はPoC期間中、継続して実施します。

### 7.2 前提・業務要件（REQ）

**目的：何のために、どこまでPoCを行うのかを決める。**

主な確認事項：

- TMT先行PoCの目的・スコープ
- Salesforce→Clouderaの開始点・終了点
- ポイント施策で必要なデータ粒度
- ニアリアルタイムの許容遅延
- 未取引客を含む対象顧客範囲
- CREATE / UPDATE / DELETE等の必要な変更種別
- PoC成功条件・証跡

技術を先に決めるのではなく、まずこの領域で「何を満たせばよいか」を明確にします。

### 7.3 Salesforce前提・データ調査（SFD）

**目的：Salesforce側でPoC可能な条件を確定する。**

主な確認事項：

- TMT Salesforce Org / Edition / 契約条件
- 既存CDC利用状況
- 対象Object / Field
- Object間の参照関係・識別キー
- 通常日・最大日・ピーク時の更新件数
- イベント配信上限
- 追加ライセンス要否

Salesforce資料に記載されている価格やイベント枠は参考情報であり、**今回の契約に適用される確定値としては扱っていません**。

### 7.4 技術方式・アーキテクチャ（ARC）

**目的：SalesforceからClouderaまでの技術的な道筋を決める。**

主な論点：

- CDCとPlatform Eventの使い分け
- Pub/Sub API等のSubscribe方式
- Salesforce→Azure認証
- Azure Event Consumer
- Azure→Cloudera連携
- E2E構成図・責務分界
- データ形式・識別情報・マッピング
- PoCで必要なログ・処理履歴

### 7.5 Security・NW・環境準備（SEC）

**目的：設計した方式を実際に接続できる状態にする。**

主な内容：

- Salesforce側権限・認証情報
- Salesforce→Azureネットワーク制約
- Azure受信環境
- Cloudera受入環境
- Secret / Credential管理
- 事前疎通確認

APIやCDCが利用可能でも、権限・ネットワーク・認証が成立しなければPoCを開始できないため、前半で並行して進める重要領域です。

### 7.6 PoC構築（DEV）

**目的：最小構成で実際にデータを流せる状態を作る。**

主な内容：

- Salesforce CDC/Event設定
- Azure Event Consumer実装
- 受信ログ・Evidence取得
- Azure→Cloudera連携処理
- Cloudera受入準備
- 単一レコードの最小E2E疎通

最初から大量データを流すのではなく、まず1レコード単位で接続経路を確認します。

### 7.7 機能・E2E検証（FT）

**目的：Salesforceで発生した変更がClouderaまで正しく到達することを確認する。**

主な検証：

- 接続・認証・Subscribe開始
- 単一変更イベント受信
- イベント内容・対象レコード識別
- Salesforce→Cloudera E2E
- 件数・値・重複の整合性
- Salesforce→Clouderaの遅延測定

「イベントが1件届いた」だけでPoC成功とはせず、ClouderaまでEnd-to-Endで確認します。

### 7.8 性能・障害検証（PT）

**目的：通常時だけでなく、負荷・障害時も含めて恒久対応として成立するか確認する。**

主な内容：

- TMT実績を基に性能試験条件を確定
- 通常負荷試験
- ピーク負荷試験
- 受信側停止・接続断・再接続
- Cloudera連携失敗時の再処理
- Replay
- 重複受信・二重処理
- 不具合修正・再試験

Replayや重複試験は採用方式・業務要件により省略可能な扱いにしています。

### 7.9 結果評価・報告（REP）

**目的：PoC結果を「実現可能かどうか」の判断材料に変える。**

主な成果：

- ○／△／×／未判定でPoC結果整理
- Salesforce利用量・追加ライセンス・コスト条件整理
- 230組織展開時の課題整理
- 恒久対応の実現可否・残課題・次アクション
- 上位報告資料
- Go／No-Go判定

### 7.10 後続展開（FUT）

**目的：STEP1完了後に230組織へ展開するための後続作業を見える化する。**

本WBSではスコープ外として日程を設定していません。

| 230組織 | 後続販社展開 | STEP2として明確に分離 |

また、このシートには「現在まだ決まっていない事項」を一覧化しています。

## 11. WBS更新時の基本ルール

### 11.1 タスクを追加するとき

1. `WBS_テンプレ` のA～C列に階層・タスク内容を入力
2. D～H列の自動表示を確認
3. I列にチームを設定
4. J列に担当者を設定
5. 必要ならK列に関連URLを設定
6. M・N列に開始日・終了日を入力
7. O列にステータスを設定
8. ガント表示を確認
9. 必要に応じて `WBS_閲覧用`、`WBS_方針変更記録`、`WBS工数配賦` へ反映

### 11.2 日程を変更するとき

日程変更時には、日付だけをずらすのではなく、次も確認します。

- 後続タスクへの影響
- 外部依存タスクへの影響
- 9月中報告への影響
- 再試験・予備期間が残っているか
- 祝日・休日を考慮しているか

### 11.3 担当者が未確定の場合

本WBSには「要確認」「ワタル／要確認」「要確認（Salesforce側）」等があります。

これは担当を推測で決めなかった箇所です。関係者合意後に実名・担当チームへ更新してください。

### 11.4 タスクを完了するとき

「作業した」だけではなく、次の状態になっているか確認します。

- 期待する成果が出ている
- 必要なレビューが完了している
- 後続タスクが開始できる
- PoC試験の場合はEvidenceが残っている
- 未解決事項がある場合は課題として記録されている

## 12. PoCで確認する成功条件

今回のPoCでは、最終的に次の観点から恒久対応の実現性を判断します。

| 観点 | 確認内容 |
|---|---|
| 接続 | SalesforceとAzure側で接続・イベント購読できるか |
| イベント | Salesforceの対象変更イベントを受信できるか |
| データ | 必要なObject・レコード・変更内容を識別できるか |
| E2E | Salesforceの変更をClouderaまで追跡できるか |
| 整合性 | 件数・値・重複等に問題がないか |
| 遅延 | Salesforce→Clouderaの実測遅延はどの程度か |
| 性能 | 通常・ピーク負荷を処理できるか |
| 障害復旧 | 接続断・受信停止・再処理等に対応できるか |
| Salesforce制約 | Object数・イベント量・契約条件上成立するか |
| コスト | 追加ライセンス等の条件を把握できるか |
| 230組織展開 | STEP2へ進む際の主要課題を整理できるか |

PoCの目的は「すべて○にすること」だけではなく、**技術・性能・運用・コスト面から実現可否を根拠付きで判断できる状態にすること**です。

## 13. PoC結果の判定イメージ

結果評価では、必要に応じて次の4段階を使用します。

| 判定 | 意味 |
|---|---|
| ○ | 要求・検証条件を満たした |
| △ | 技術的には成立したが、条件・課題が残る |
| × | 現方式では要求を満たせない |
| 未 | 未検証、または判断材料不足 |

例えば、「Azureまでイベントは受信できるがピーク負荷時に遅延する」という場合、単純な失敗ではなく「△：条件付き成立」として課題を明確にする考え方です。

## 15. 用語集

### Salesforce

顧客情報・活動情報等を管理するクラウド型CRMプラットフォームです。今回のPoCではデータ連携元となります。

### TMT

今回のSTEP1で先行PoC対象としているSalesforce組織です。資料上では230組織の中で最大規模として扱われています。

### PoC

Proof of Conceptの略です。日本語では「概念実証」と呼ばれます。

本番システムを完成させる前に、「この方式で本当に実現できるか」を小さな範囲で検証します。

### CDC

Change Data Captureの略です。

Salesforce上でデータが作成・更新・削除された等の変更をイベントとして外部へ通知するための仕組みです。

### Event Bus

イベントをPublish（発行）し、Subscriber（購読者）が受け取るためのイベント基盤です。

### Publish

イベントを「発行する」ことです。

### Subscribe

イベントを「購読・受信する」ことです。

### Event Consumer

イベントを受信して処理する側の仕組みです。本WBSではAzure側の受信処理を指す表現として使用していますが、具体的なAzureサービスは未確定です。

### Cloudera DWH

今回のSTEP1でSalesforceデータを到達させる基本的な終了点として扱っているデータ基盤側のDWHです。

### E2E（End-to-End）

途中だけではなく、最初から最後まで一連の流れを確認することです。

今回であれば、Salesforceでデータを変更してからClouderaで確認できるところまでを意味します。

### Replay

一時的にイベントを受信できなかった場合などに、保持されたイベントを再取得する考え方・機能です。

今回のPoCで必ず実施すると確定しているわけではなく、採用方式・要件に応じて判断します。

### Go／No-Go

PoC結果を基に、「次のフェーズへ進むか／現方式のままでは進まないか」を判断することです。

## 16. よくある質問

### Q1. このWBSの通りに実施すれば、230組織への本番展開まで完了しますか？

いいえ。

今回の主対象はTMTでのSTEP1 PoCです。230組織への詳細設計・実展開・本番運用設計はSTEP2として別途計画します。

### Q2. SalesforceのCDCを使うことは確定していますか？

イベント駆動方式の有力候補ですが、具体的な使い方は未確定です。

CDC Change Eventを直接Subscribeするのか、別のPlatform Eventを介すのかを含め、ARCタスクで確認します。

### Q3. Azure Functionsを使うことは決まっていますか？

決まっていません。

本WBSでは「Azure Event Consumer」として必要な役割を定義していますが、具体的なAzureサービスは方式検討後に確定します。

### Q4. 9月30日までに必ず完成させる計画ですか？

9月30日はWBS上の仮完了日であり、正式納期ではありません。

正式日程確認後に更新します。

### Q5. 工数欄が未算定なのはなぜですか？

対象Object数やアーキテクチャが未確定の状態で旧工数を流用すると、見積精度が低くなるためです。

方式・対象・担当体制確定後に `WBS工数配賦` を利用して再見積します。

### Q6. 「活動4オブジェクト」を前提に進めてよいですか？

現時点では確定扱いしません。

Salesforce検討資料では候補として示されていますが、対象Object / Fieldは別途確認するタスクとしてWBSに入れています。

### Q7. 「ニアリアルタイム」は何秒以内ですか？

現時点では数値基準が未確定です。

REQ-04で業務側の許容遅延を確認し、その値とPoCの実測遅延を比較します。

## 18. まとめ

このWBSは、単なる作業一覧ではなく、

> **「Salesforce→Azure→Clouderaの恒久的なイベント連携が実現可能かを、TMTで根拠を持って判断するためのPoC計画」**

です。

進め方の基本は次の順序です。

```text
前提・業務要件を確定
        ↓
Salesforceデータ・契約条件を確認
        ↓
イベント連携方式・E2E構成を決定
        ↓
権限・NW・環境を準備
        ↓
最小構成でPoCを構築
        ↓
機能・E2Eを確認
        ↓
性能・障害を確認
        ↓
結果・コスト・230組織課題を整理
        ↓
Go／No-Goを判断
```

未確定事項を推測で埋めるのではなく、**「未確定であることを見える化し、確認タスクとして管理する」**ことが本WBSの重要な考え方です。
