# MDBファイルを取り込み、異なるテナントのSharePoint間でファイル移動を自動化する方法の調査

- **調査時点**：2026年7月28日
- **調査対象**：Microsoft AccessのMDBファイルを、異なるMicrosoft 365テナントのSharePoint間で自動移動できるか
- **確認した移動方式**：MDBファイルを開かず、ファイル形式を維持したまま移動する
- **背景・目的**：異なるテナント間のファイル移動を自動化し、手作業、移動漏れ、誤操作を減らす
- **調査方法**：Microsoft公式ドキュメントを中心とした机上調査

> [!IMPORTANT]
> 本資料は、2026年7月28日時点で公開されているMicrosoft公式仕様を基にした机上調査結果です。実際のMicrosoft 365テナント、SharePointサイト、接続アカウント、セキュリティ設定、MDBファイルを使用した動作検証は行っていません。

---

## 1. 調査背景・目的

今回のチケットでは、Microsoft AccessのMDBファイルを、移動元テナントのSharePointから、異なる移動先テナントのSharePointへ自動で移動できるかを調査する。

三ツ井さんへの確認により、次の前提が明確になった。

- MDBファイルは開かず、ファイルのまま移動する
- MDB内部のテーブルやデータをCSV・Excelなどへ変換しない
- 移動元と移動先は、それぞれ異なるMicrosoft 365テナントのSharePointである
- 移動先への保存が成功した後、必要に応じて移動元ファイルを削除する
- SharePoint上のバージョン履歴、共有リンク、固有権限などの完全移行は、現時点では主目的としない

今回の自動化では、MDBファイルをバイナリファイルとして取り扱う。

そのため、ファイルの移動だけであれば、Microsoft AccessやAccess Database Engineを自動処理の実行環境へ導入する必要はないと考えられる。

一方、今後、次のような要件が追加された場合は、ファイル移動とは別の処理として調査・設計する必要がある。

- MDB内部のテーブルを読み取る
- 特定のデータが含まれている場合だけ移動する
- MDBが正常に開けることを自動判定する
- MDBからCSVやExcelを生成する
- MDBのパスワード保護や暗号化状態を解析する

## 2. 結論

### 2.1 そもそもできるのか

**条件付きで可能と考えられる。**

必要な認証、権限、クロステナント接続、SharePointの外部共有設定、ファイルサイズなどの条件を満たせば、異なるMicrosoft 365テナントのSharePoint間でMDBファイルを自動移動できる可能性は高い。

ただし、異なるテナント間で1回の「移動」操作を行うのではなく、次の処理を組み合わせて移動を実現する。

```text
移動元SharePointからMDBを取得
  ↓
移動先SharePointへMDBを新規作成
  ↓
移動先への保存結果を確認
  ↓
正常時のみ移動元MDBを削除
```

したがって、実際の処理は「移動先へコピーして、成功を確認した後に移動元を削除する」構成となる。

### 2.2 可否判定

| 方法 | MDBファイルのクロステナント移動 | 判定 |
|---|---:|---|
| Power Automate＋SharePointコネクタ | 条件付きで可能 | 第一候補。両テナントへの接続、権限、サイズ制限の確認が必要 |
| Microsoft Graph API | 可能 | 大容量、分割転送、途中再開、厳密な再試行が必要な場合の候補 |
| Azure Logic Apps＋SharePointコネクタ | 条件付きで可能 | Azure上での監視・管理を重視する場合の候補 |
| Azure Blob Storage中継 | 条件付きで可能 | 送信側と受信側の処理を分離する場合の候補 |
| Power Automate for desktop／OneDrive同期 | 条件付きで可能 | 暫定・小規模向け。端末依存と保守負担がある |
| Microsoft公式クロステナントSharePoint移行 | 今回の用途には不向き | サイト全体の一括移行向け |
| 担当者による手動移動 | 可能 | 自動転送が許可されない場合の最終代替 |

### 2.3 最終的な回答

> **MDBファイルを開かず、ファイルのまま異なるテナントのSharePointへ移動することは、技術的には実現可能と考えられる。**
>
> **第一候補は、Power Automateで「取得 → 作成 → 確認 → 成功時のみ削除」を実行する方法である。**
>
> **ただし、実際の採用可否は、Power Platformのテナント分離、Microsoft Entra ID、SharePointの外部共有、接続アカウントの権限、MDBファイルサイズを実環境で確認した後に判断する必要がある。**

## 3. できる場合のおおよその方法

### 3.1 全体構成

```text
移動元テナントのSharePoint
  ↓
MDBファイルの登録を検知
  ↓
対象が「.mdb」ファイルか判定
  ↓
移動元からファイル情報・ファイル内容を取得
  ↓
移動先テナントのSharePointへファイルを作成
  ↓
ファイル名・ファイルサイズ・保存先を確認
  ↓
正常時のみ移動元ファイルを削除
  ↓
処理結果をログへ記録
  ↓
失敗時はTeamsまたはメールで通知
```

### 3.2 各機能の役割

| 機能 | 役割 |
|---|---|
| 移動元SharePoint | MDBファイルの保管、登録検知、ファイル内容の取得、移動後の削除 |
| Power Automate | ファイル検知、条件判定、取得、作成、結果確認、削除、通知を制御 |
| 移動先SharePoint | MDBファイルの保存、保存結果の確認 |
| Microsoft Entra ID | 移動元・移動先テナントのユーザーやアプリの認証・アクセス制御 |
| Power Platform管理設定 | Power Automateのクロステナント接続を許可または制限 |
| SharePointリスト等 | 処理日時、移動元、移動先、サイズ、成功・失敗、エラー内容を記録 |
| Teams／メール | 処理失敗、認証切れ、未処理ファイルなどを担当者へ通知 |

### 3.3 処理の流れ

1. 移動元テナント、移動先テナント、対象SharePointサイト、ライブラリ、フォルダーを特定する。
2. 移動元SharePointでMDBファイルの登録を検知する。
3. ファイル名を確認し、拡張子が`.mdb`または`.MDB`であることを判定する。
4. 移動元SharePointからファイル名、ファイルID、パス、サイズ、更新日時、ETagなどを取得する。
5. 移動元SharePointからMDBファイル本体をバイナリデータとして取得する。
6. 移動先テナントのSharePoint接続を使用し、同じファイル名でファイルを作成する。
7. 移動先のファイル名、ファイルサイズ、保存先を確認する。
8. 必要に応じて、移動先のMDBファイルをMicrosoft Accessで開けることを検証する。
9. 移動先への保存が正常に完了した場合だけ、移動元ファイルを削除する。
10. 処理日時、移動元、移動先、ファイルサイズ、処理結果、削除結果、エラー内容をログへ記録する。
11. 処理に失敗した場合は、移動元ファイルを残し、Teamsまたはメールで担当者へ通知する。

### 3.4 移動で保持される主な内容／引き継がれない内容

| 移動で保持できる主な内容 | 引き継がれない内容・注意点 |
|---|---|
| MDBのファイル名・拡張子 | SharePointのバージョン履歴は原則として引き継がれない |
| MDBファイル本体のバイナリ内容 | 元の作成者・更新者は移動先で新規作成したアカウントとなる |
| MDB内部のテーブル・データ構造 | 元の作成日時・更新日時はそのまま保持されない可能性がある |
| ファイルサイズ | 元テナントの共有リンク、固有権限、監査履歴は引き継がれない |
| 設計した場合のフォルダー構成 | SharePoint列、承認状態、保持・秘密度設定は別途設定が必要 |

ファイルサイズが一致しても、内容の完全一致を数学的に証明するものではない。

小規模検証では、ファイル名とサイズの一致に加え、移動先のMDBを正常に開けることを確認する。より厳密な検証が必要な場合は、移動前後のハッシュ値比較を別途検討する。

## 4. 異なるテナントのSharePointへ接続する方法

### 4.1 Power Automateのクロステナント接続

Power Automateでは、概念上、次の2つのSharePoint接続を使用する。

| 接続 | 主な用途 |
|---|---|
| 移動元テナント用のSharePoint接続 | ファイル検知、情報取得、内容取得、削除 |
| 移動先テナント用のSharePoint接続 | ファイル作成、保存結果の確認 |

Power Platformのテナント分離が無効で、移動先テナントへアクセスできる適切なMicrosoft Entra IDの認証情報を使用できる場合は、クロステナント接続を作成できる可能性がある。

一方、テナント分離が有効で、移動先テナントが許可されていない場合は、正しい認証情報やSharePoint権限を持っていても接続が拒否される可能性がある。

確認が必要な設定は次のとおりである。

- Power Platformのテナント分離の有無
- 移動元から移動先へのアウトバウンド接続許可
- 必要に応じた移動先側のインバウンド接続許可
- 対象テナントIDまたはドメインの許可設定
- Power Platformのデータポリシー
- SharePointコネクタの利用可否

### 4.2 Microsoft Entra ID・SharePointの設定

クロステナント接続では、Power Platformだけでなく、Microsoft Entra IDとSharePointの設定も影響する。

#### Microsoft Entra ID

確認する主な項目は次のとおりである。

- 移動元テナントのアウトバウンドアクセス
- 移動先テナントのインバウンドアクセス
- 対象ユーザー・グループ・アプリケーションが許可されているか
- 多要素認証の要求
- 管理対象端末・準拠端末の要求
- 接続元IPアドレスの制限
- サインイン頻度
- 外部コラボレーションの許可・拒否ドメイン

#### SharePoint

SharePointの外部共有は、組織全体と個別サイトの両方で制御される。

確認する主な項目は次のとおりである。

- 組織全体の外部共有設定
- 移動先サイトの外部共有設定
- 新規ゲスト・既存ゲストの利用可否
- 許可・拒否ドメイン
- サイトアクセス制限
- 接続アカウントに付与できる読み取り・作成・削除権限

個人アカウントをPower Automateの接続に使用すると、異動、退職、アカウント停止、パスワード変更などによってフローが停止する可能性がある。

本番運用では、自動処理用の専用アカウント、接続の共同所有、接続切れの監視などを検討する。

### 4.3 ファイルサイズとファイル受け渡し

Microsoft公式情報では、Power Automateの通常のメッセージサイズ上限は**100MB**である。

ファイルをコネクタ経由で送信する場合は、ファイル本体だけではなく、処理全体のペイロードが100MB未満である必要がある。

そのため、100MB未満のMDBであっても、使用するアクションや付随情報によっては制限へ達する可能性がある。

| MDBファイルのサイズ | 現時点の判断 |
|---|---|
| 数MB～数十MB | Power Automateの有力候補 |
| 100MB付近 | 実ファイルによる小規模検証が必要 |
| 100MB超 | Microsoft Graph APIを優先的に検討 |
| 今後増加する見込み | Graph APIを含めて方式を比較 |

Microsoft Graphでは、250MB以下のファイルを単一要求でアップロードできる。

250MBを超えるファイルや、通信切断後の再開が必要な場合は、アップロードセッションを使用し、ファイルを複数の範囲へ分けて転送できる。1回の要求で送信する範囲は60MiB未満とする必要がある。

## 5. 現時点での推奨案

### 5.1 初期段階の推奨：Power Automateによる小規模検証

現時点では、Power Automateを第一候補とし、テスト用のSharePointフォルダーと代表的なMDBファイルを使用した小規模検証を行う。

最初からファイル登録時の自動実行にせず、問題箇所を切り分けやすい手動起動のフローで確認する。

```text
手動で検証開始
  ↓
対象MDBを指定
  ↓
移動元からファイル情報・内容を取得
  ↓
移動先へファイルを作成
  ↓
ファイル名・サイズを比較
  ↓
MDBを正常に開けるか確認
  ↓
成功時だけ移動元を削除
  ↓
ログ記録・通知
```

#### 推奨理由

- SharePointの標準コネクタを利用できる
- ローコードで比較的短期間に検証できる
- MDB内部を解析する必要がない
- 取得、作成、確認、削除の処理を画面上で確認しやすい
- ログやTeams・メール通知を追加しやすい
- 最初からGraph APIを開発するより、実現可否を小さく確認できる
- ファイルサイズ、接続、権限に問題がなければ、そのまま本番方式の候補にできる

小規模検証では、少なくとも次を確認する。

- 移動元・移動先の両SharePointへ接続できる
- 小容量MDBを移動先へ作成できる
- 移動前後のファイル名とサイズが一致する
- 移動先のMDBを正常に開ける
- 移動先への保存に失敗した場合、移動元が削除されない
- 同名ファイルで意図しない上書きが発生しない
- 同じファイルを再実行しても重複・誤削除が発生しない
- 現在想定される最大サイズのMDBを転送できる
- 日を空けても接続が継続して使用できる
- エラー時にログと通知が残る

### 5.2 大容量・大量処理の場合：Microsoft Graph API

次の条件に該当する場合は、Microsoft Graph APIを第二候補とする。

- MDBファイルがPower Automateの制限を超える
- ファイルサイズが将来的に増える
- 大量ファイルを処理する
- 分割転送や途中再開が必要
- ユーザーアカウントへ依存しない無人実行が必要
- 再試行、重複防止、監査ログを細かく実装したい
- Power Platformの制約によりPower Automate接続を利用できない

Graph API方式では、次の準備が必要になる。

- Microsoft Entra IDのアプリ登録
- 移動元・移動先テナントでのアプリ権限
- 両テナント管理者による同意
- クライアントシークレットまたは証明書
- Azure Functions、Azure Logic Appsなどの実行基盤
- アクセストークン取得処理
- APIエラー、スロットリング、再試行処理
- 資格情報の期限管理
- ログ、監視、障害復旧の設計

Power Automateより柔軟である一方、開発・運用・セキュリティ設計の負担は大きくなる。

### 5.3 自動転送が許可されない場合：手動移動＋自動通知

組織のセキュリティ規程で、外部テナントへの自動的なファイル転送が禁止されている場合は、Power Automate、Graph API、Logic Appsへ方式を変更しても解決しない。

この場合は、次の部分だけを自動化する。

```text
MDBファイルの登録を検知
  ↓
担当者へTeamsまたはメールで通知
  ↓
担当者が移動先SharePointへ手動アップロード
  ↓
作業完了を記録
  ↓
未完了または期限超過の場合は再通知
```

完全自動化ではないが、自動処理へ広い権限を付与できない場合の現実的な代替案となる。

## 6. 現時点で阻害・課題になりそうなこと

### 6.1 外部テナントへのファイル転送に関する組織規程

最も重要な確認事項である。

技術的に接続できても、次のような規程に該当する場合は自動化できない。

- 機密情報を外部テナントへ保存してはならない
- 外部テナントへの転送には事前承認が必要
- 承認されていないクラウド環境へ保存してはならない
- 自動処理用アカウントを利用してはならない
- Azure Blob Storageなどの中継領域へ保存してはならない

#### 影響

- 方式に関係なく自動転送を実施できない
- Power AutomateからGraph APIへ変更しても解決しない
- 技術検証前にセキュリティ・コンプライアンス確認が必要になる

#### 対応候補

- MDBに含まれる情報の機密区分を確認する
- 移動先テナントの管理主体を確認する
- セキュリティ部門へ転送可否を確認する
- 必要に応じて例外申請を行う
- 許可されない場合は、手動移動＋自動通知へ切り替える

### 6.2 Power Platformのテナント分離

Power Platformのテナント分離が有効で、移動先テナントが許可されていない場合、Power Automateから移動先SharePointへの接続が拒否される可能性がある。

#### 影響

- 移動先テナントのSharePoint接続を作成できない
- フローを保存または実行できない
- 管理者の設定変更によって、既存フローが後から停止する可能性がある

#### 対応候補

- テナント分離の有無を確認する
- 対象テナントの許可方向を確認する
- 必要に応じて対象テナントを許可設定へ追加する
- 設定変更できない場合はGraph APIを検討する

ただし、Graph APIに切り替えても、Microsoft Entra IDや組織規程の制限は残る。

### 6.3 Microsoft Entra IDのクロステナントアクセス

Microsoft Entra IDでは、外部テナントに対する受信・送信アクセスを、ユーザー、グループ、アプリケーション単位で制御できる。

#### 影響

- 移動先テナントへサインインできない
- ゲストユーザーを利用できない
- アプリ認証によるGraph APIアクセスが拒否される
- MFAや準拠端末の条件を満たせず接続できない

#### 対応候補

- 移動元のアウトバウンドアクセスを確認する
- 移動先のインバウンドアクセスを確認する
- 対象ユーザー・アプリケーションの許可状態を確認する
- MFA、端末、IPアドレス、サインイン頻度の条件を確認する

### 6.4 SharePointの外部共有設定

SharePointの外部共有は、組織レベルとサイトレベルの両方で制御される。

#### 影響

- 移動先サイトへ接続できない
- ゲストユーザーを追加できない
- ファイルの作成権限を付与できない

#### 対応候補

- 組織全体の外部共有設定を確認する
- 移動先サイトの外部共有設定を確認する
- 許可・拒否ドメインを確認する
- 対象アカウントがサイトへアクセスできるか確認する

### 6.5 条件付きアクセス・MFA

条件付きアクセスにより、次の制限が設定されている可能性がある。

- 定期的なMFA
- 管理対象端末・準拠端末の必須化
- 接続元IPアドレスの制限
- サインイン頻度
- 利用規約への再同意
- 特定クライアントアプリの制限

#### 影響

- 接続の作成時に認証エラーが発生する
- 初回は動作しても、後日認証切れで停止する
- 無人実行中に再認証できず、ファイルが滞留する

#### 対応候補

- SharePointとPower Automateの条件付きアクセスを確認する
- 専用アカウントの利用条件を確認する
- 接続切れを監視し、担当者へ通知する
- Graph APIでは証明書を利用したアプリケーション認証を検討する

### 6.6 MDBファイルのサイズ

Power Automateでは、コネクタを通して送信するペイロード全体に100MBの通常上限がある。

#### 影響

- ファイル内容の取得に失敗する
- 移動先へのファイル作成に失敗する
- 小さいファイルは成功し、大きいファイルだけ失敗する

#### 対応候補

- MDBの平均・最大サイズを確認する
- 最大サイズに近い実ファイルで検証する
- 100MB超の場合はGraph APIを優先する
- 250MB超または再開処理が必要な場合はアップロードセッションを検討する

### 6.7 SharePointの権限

今回の処理では、次の操作に必要な権限が求められる。

| 対象 | 必要な操作 |
|---|---|
| 移動元 | ファイル情報の参照 |
| 移動元 | ファイル本体の取得 |
| 移動元 | 保存成功後の削除 |
| 移動先 | フォルダーの参照 |
| 移動先 | ファイルの新規作成 |
| 移動先 | 作成結果の確認 |
| 移動先 | 必要に応じた上書き |

#### 影響

- 取得はできるが削除できない
- 移動先を参照できるがファイルを作成できない
- 一部のフォルダーだけ処理に失敗する

#### 対応候補

- 読み取り、作成、削除を個別に検証する
- 対象ライブラリ・フォルダーに必要な権限だけを付与する
- Graph APIではSelected権限による範囲限定を検討する

### 6.8 保持ポリシー・保持ラベル

Microsoft Purviewの保持ポリシーや保持ラベルによって、移動元ファイルを削除できない可能性がある。

#### 影響

- 移動先へのコピーは成功するが、移動元にファイルが残る
- 「移動」ではなく「コピー」状態になる
- 削除済みと見えても、コンプライアンス用領域へ保持される場合がある

#### 対応候補

- 対象ライブラリの保持設定を確認する
- 削除を必須要件とするか見直す
- 削除できない場合は処理済みフォルダーへ移す
- 処理済みフラグやコピー済み管理を検討する

### 6.9 同名ファイル・二重実行

移動先に同名ファイルがある場合や、同じファイルを複数回処理した場合のルールが必要である。

#### 影響

- 既存ファイルを意図せず上書きする
- 同じMDBが複数作成される
- 再実行時に誤って移動元を削除する

#### 対応候補

- 初期検証では同名ファイルがある場合はエラーとする
- 元ファイルIDを処理履歴へ保存する
- 処理中、成功、失敗の状態を管理する
- 必要に応じて日時や連番を付けて別名保存する
- フローの同時実行数を制限する

### 6.10 更新途中のMDBファイル

SharePointへのアップロードや、別システムによる更新が完了する前に取得すると、不完全なファイルを移動する可能性がある。

#### 影響

- ファイルサイズが確定する前に取得する
- 移動先のMDBが正常に開けない
- 転送中に内容が変更される

#### 対応候補

- ファイル登録後、一定時間待ってから処理する
- 時間を空けて2回ファイルサイズを確認する
- 転送可能フォルダーへ配置されたファイルだけ処理する
- 更新日時やETagを取得前後で確認する
- 移動先でMDBを開けることを検証する

### 6.11 メタデータ・バージョン履歴

ファイル本体を取得し、移動先で新規作成する方式では、SharePoint上の情報は完全に引き継がれない。

主に次の情報が対象となる。

- バージョン履歴
- 元の作成者・更新者
- 元の作成日時・更新日時
- 共有リンク
- 固有権限
- SharePoint列
- 承認状態
- 監査履歴

これらが必要な場合は、必要な項目だけをPower AutomateまたはGraph APIで再設定するか、移行専用ツールを検討する。

## 7. できない場合・適さない場合の代替手段

### 7.1 代替案一覧

| 代替案 | 継続的な自動移動 | 大容量対応 | 実装負担 | 主な特徴 |
|---|---:|---:|---:|---|
| A：Power Automate | 可能 | 制限を受けやすい | 低～中 | 第一候補。ローコードで検証しやすい |
| B：Microsoft Graph API | 可能 | 適している | 中～高 | 分割転送、途中再開、詳細な制御が可能 |
| C：Azure Logic Apps | 可能 | 構成による | 中 | Azure上での監視・管理に向く |
| D：Azure Blob Storage中継 | 可能 | 比較的適している | 中～高 | 送信側・受信側を分離しやすい |
| E：Power Automate for desktop／同期フォルダー | 条件付きで可能 | 端末・同期に依存 | 中 | 暫定・小規模向け |
| F：Microsoft公式クロステナント移行 | 継続用途には不向き | サイト移行向け | 高 | サイト全体の一括移行に向く |
| G：手動移動＋自動通知 | 一部のみ自動 | 人手に依存 | 低 | 自動転送が禁止されている場合の代替 |

### 7.2 Power Automateが利用できない場合

Power Automateが利用できない理由によって、代替手段を分ける。

- Power Platformのテナント分離だけが問題  
  → Microsoft Graph APIを検討する
- 接続アカウントの継続運用が難しい  
  → Graph APIのアプリケーション認証を検討する
- Azure側で監視・運用したい  
  → Azure Logic Apps＋Graph APIを検討する
- 1つの処理から両テナントへ接続できない  
  → Azure Blob Storage中継を検討する

### 7.3 大容量ファイルの場合

MDBファイルがPower Automateのサイズ制限に抵触する場合は、次の順で検討する。

1. Microsoft Graph APIの単一要求によるアップロード
2. Microsoft Graph APIのアップロードセッション
3. Azure Blob Storageを利用した一時保管・分離構成
4. 大量・一括移行の場合は移行専用ツール

### 7.4 外部転送が禁止されている場合

別テナントへのファイル転送自体が組織規程で禁止されている場合は、技術方式を変更しても解決しない。

この場合は、次を検討する。

- セキュリティ部門へ例外申請する
- 承認された中継領域を使用する
- ファイル移動は担当者が行う
- MDB登録時の通知、未処理管理、期限超過通知だけを自動化する

## 9. 最終的な推奨方針・まとめ

### 9.1 今回のチケットに対する回答

> MDBファイルを開かず、ファイルのまま異なるMicrosoft 365テナントのSharePointへ移動することは、条件付きで実現可能と判断する。
>
> 第一候補は、Power AutomateのSharePointコネクタを利用し、移動元から取得したMDBを移動先へ作成し、保存結果を確認した後に移動元を削除する方法である。

### 9.2 初期運用の推奨

> 初期段階では、本番フォルダーを使用せず、テスト用SharePointフォルダーと代表的なMDBを使った小規模検証を推奨する。
>
> 最初は手動起動のフローで、クロステナント接続、ファイル取得、ファイル作成、サイズ確認、失敗時制御、成功時削除を順番に確認する。

### 9.3 Power Automateで難しい場合の推奨

> MDBファイルが100MBを超える場合、分割転送や途中再開が必要な場合、接続アカウントへ依存しない無人実行が必要な場合は、Microsoft Graph APIを優先して検討する。
>
> 同一の処理から両テナントへ接続できない場合は、Azure Blob Storageを中継し、送信側と受信側の処理を分離する。

### 9.4 中長期的な推奨

> 本番運用では、個人アカウントへの依存を避け、接続・資格情報の期限監視、ログ、エラー通知、再実行手順を整備する。
>
> ファイル数やサイズが増加した場合は、Power AutomateからGraph APIへの切り替え基準を事前に決めておく。

### 9.5 要点

- **異なるテナントのSharePoint間でMDBファイルを移動することは条件付きで可能**
- **第一候補はPower Automate**
- **実際の処理は「取得 → 作成 → 確認 → 成功時のみ削除」**
- **MDB内部を解析しない場合、Microsoft AccessやAccess Database Engineは原則不要**
- **最大の確認事項は、組織規程、テナント分離、Entra ID、SharePoint外部共有、権限、ファイルサイズ**
- **Power Automateの通常メッセージサイズは100MBで、ファイル本体だけでなくペイロード全体が対象**
- **100MB超や高度な制御が必要な場合はMicrosoft Graph APIが有力**
- **同一処理から両テナントへ接続できない場合はBlob Storage中継を検討**
- **外部自動転送が禁止される場合は、手動移動＋自動通知が代替案**
- **本番採用前に、代表的なMDBを使った小規模検証が必要**
