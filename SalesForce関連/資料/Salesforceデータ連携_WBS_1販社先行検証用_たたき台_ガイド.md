# Salesforceデータ連携
# 1販社先行検証用WBS ガイド

## 1. この資料について

今回、Salesforceデータ連携の進め方を「最初から2販社へ展開する計画」から、「まず1販社でNiFiによるデータ連携を先行検証する計画」へ見直し、WBSのたたき台を作成しました。

対象ファイルは次のとおりです。

> `Salesforceデータ連携_WBS_1販社先行検証用_たたき台.xlsx`

このWBSは、現時点で確認できている会議方針と見積書をもとに、1販社のSalesforceデータをNiFiで取得し、CDPへ保存・確認するまでの作業を整理したものです。

一方で、先行対象となる販社名、対象Object、担当者、正式な開始日など、まだ決まっていない内容もあります。そのため、完成版の実行計画ではなく、関係者と内容を確認しながら具体化していくための最初のたたき台として位置付けています。

---

## 2. WBSの基本方針

今回のWBSでは、次の内容を基準としています。

| 項目 | 基準 |
|---|---|
| 対象 | 先行する1販社 |
| 連携元 | Salesforce |
| 連携処理 | NiFi |
| 保存・確認先 | CDP |
| 対象環境 | 検証環境 |
| 基準工数 | 53.5人日 |
| 条件付き工数 | 4.0人日 |
| 仮の計画期間 | 2026年8月3日～2026年9月18日 |
| リードタイム | 約1.5か月 |
| 号口反映 | 先行検証後に実施可否を判断 |
| 2販社目 | 先行検証後に実施可否を判断 |
| Power BI | 先行検証の必須範囲外 |
| CDC・Streaming | 将来対応 |

データ連携の全体像は次のとおりです。

```text
Salesforce
    ↓
NiFiで接続・データ取得
    ↓
必要な処理・技術情報の付与
    ↓
CDPへデータを保存
    ↓
件数・主要項目・エラー・再実行を確認
    ↓
先行検証結果と後続展開の課題を整理
```

## 3. 今回の見直し内容

### 3.1 元のWBS

元のたたき台は、次の前提で作成していました。

- 2販社を対象とする
- 検証環境と号口環境の両方へ対応する
- 2販社目の設定も同一計画内で実施する
- 号口移行、初回データ取得、定期実行、初期監視まで行う
- 計画期間は2026年8月3日～2026年10月16日

### 3.2 現在のWBS

現在のWBSでは、まず1販社の検証へ対象を絞っています。

- 1販社のSalesforce接続
- NiFiによるデータ取得
- CDPへのデータ保存
- 件数・主要項目の確認
- Retry・再実行・重複防止の確認
- セキュリティ・ネットワークの確認
- 先行検証の結果整理
- 号口・2販社目・追加販社への展開判定

### 3.3 開発期間を短縮できる理由

元の2販社対応WBSで通常作業としていた次の内容を、先行検証後の条件付き・後続対応へ移しています。

- 2販社目のデータ取得・保存設定
- 2販社を対象とした販社別の試験
- 号口環境へのCredential・Connection設定
- NiFi処理の号口反映
- 号口環境での初回データ取得
- 定期実行スケジュールの有効化
- 号口反映後の初期監視
- 複数販社展開に向けた最終的な共通化・標準化

これにより、計画上の期間は次のように変わっています。

| 計画 | 期間 |
|---|---|
| 元の2販社対応WBS | 2026年8月3日～2026年10月16日 |
| 1販社先行検証WBS | 2026年8月3日～2026年9月18日 |
| 短縮幅 | 約4週間 |

今回のWBSは、リードタイムの期待値である約1.5か月に収まる計画になっています。

ただし、日程には大きな余裕があるわけではありません。外部準備や関係者確認が予定どおり進み、複数の作業を並行して進められることが前提です。

## 7. タスク区分の見方

## 7.1 通常

1販社先行検証の基準範囲で実施する作業です。

例：

- Salesforceデータ調査
- NiFi接続
- CDP保存設計
- NiFiフロー実装
- 単体試験
- E2E試験

## 7.2 外部依存

関係者や外部環境の準備が必要な作業です。

例：

- Salesforce Sandboxの準備
- Salesforce認証情報の準備
- セキュリティ要件の提示
- 先行販社・Orgの確定

外部依存が遅れると、後続の設計・開発・試験へ影響します。

## 7.3 マイルストーン

作業開始や完了を判断するポイントです。

主なマイルストーンは次のとおりです。

- 1販社先行検証の着手判定
- 先行検証完了・号口／追加販社展開判定

## 7.4 条件付き

要件や先行検証結果によって、実施するかどうかが変わる作業です。

例：

- 2販社目の設定
- Watermark
- Incremental Load
- 削除データ連携
- Private接続
- 号口反映

条件が決まる前に、通常作業として日程や工数へ含めないようにします。

## 7.5 対象範囲確認

別資料には含まれているものの、1販社先行検証の基準範囲には確定していない作業です。

例：

- ADLS
- Bronze
- Silver
- Gold
- Power BI

正式に追加する場合は、影響範囲と追加工数を確認します。

## 7.6 将来対応

今回の先行検証では実装せず、後続で方針整理・改善する内容です。

例：

- CDC
- Streaming
- 追加販社展開の標準化

## 9. WBSの更新方法

## 9.1 担当が決まったとき

次の列を更新します。

- I列：主担当チーム
- J列：主担当者

担当者を複数名並べるのではなく、進捗と完了を管理する主担当者を設定します。

## 9.2 作業日程が決まったとき

次の列を更新します。

- M列：開始日
- N列：終了日

正式な日程へ変更した場合は、`WBS_閲覧用`と`WBS_タスク補足`の内容も確認します。

## 9.3 作業を開始したとき

O列のステータスを次のように変更します。

> 準備中 → 進行中

あわせて、関連チケットや資料がある場合はK列へURLを設定します。

## 9.4 作業が完了したとき

完了条件を`WBS_タスク補足`で確認してから、ステータスを`完了`へ変更します。

単に作業を実施しただけではなく、次の内容が揃っていることを確認します。

- 成果物
- レビュー結果
- テストEvidence
- 関係者の確認
- 必要な記録
- 後続作業への引継ぎ

## 9.5 条件付き作業を採用するとき

次の順番で対応します。

1. 実施条件が成立したか確認する
2. 対象範囲を決める
3. 追加工数を確認する
4. 担当者を設定する
5. 開始日・終了日を設定する
6. 通常作業として扱うか判断する
7. WBSと工数表を更新する

号口反映や2販社目を採用する場合は、現在の53.5人日とは分けて再計画します。

3. 現在進行中のタスク
4. 終了日を超過しているタスク
5. 担当者が未設定のタスク
6. 条件付き作業の採否

8. 先行検証の完了条件
9. 号口・2販社目・追加販社への展開判断

会議では、タスク名だけでなく、タスクIDを使って確認すると認識を合わせやすくなります。

## 13. まとめ

今回のWBSのポイントは次のとおりです。

- 2販社同時対応ではなく、1販社の先行検証へ対象を絞っている
- SalesforceからNiFiを経由してCDPへ保存する流れを対象としている
- 基準工数は53.5人日
- 号口リリース4人日は条件付き

- 2販社目・号口・追加販社展開は、先行検証後に判断する
- 第一リリース資料51.5人日は合算せず、作業分解と漏れ確認に使用している
- ADLS、Bronze、Silver、Gold、Power BIは基準範囲外または確認対象
- 未確定の担当者・対象データ・正式日程は推測で設定していない
- 正式な管理元は`WBS_テンプレ`
- 会議での確認には`WBS_閲覧用`を使用する
